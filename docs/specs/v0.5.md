1. `claude plugin validate --strict` passes for both editions.
2. Evals T0, T1, T2, T3 pass on the built artifact, in the repo's `evals/` harness.
3. The claude.ai upload is v0.5 and T0 passes in a fresh cloud Cowork session (skills listed, SessionStart injects the house rules).
4. No skill contradicts the GTT policy below (checked by a T9 grep eval).
5. README, `plugin.json` and `marketplace.json` describe both editions.

### W3. Fold in learnings (roadmap fix 3)

**3a. GTT policy in gtt-audit and crash-protocol** (replaces "stop on everything" and "tighten in a fall"):
1. Index and commodity ETFs: no stop; single-leg target only.
2. Hold/add stocks: crash-floor stop about 25% below price, never closer than about 20%.
3. EXIT/REDUCE verdicts: single-leg exit at the written level, no stop.
4. No verdict means default hold, so rule 2 applies.
5. Every audit runs a crash test: which stops fire at a uniform -10% and -20%. Target: no hold/add name fires at -20%.
6. GTT quantity must equal held quantity, per symbol (hard step, not discretionary). Flag the inverse case (GTT qty > held) too.
7. Stop-width outlier check: flag any stop much tighter than the book's own convention.

The thresholds are defaults; `portfolio-profile.md` overrides them (house rule 7). crash-protocol drops "propose trailed SLs" and adds "which stops would force-sell a hold name; propose widening them to crash-floor".

**3b. GTT mechanics**
- `get_gtts`: always page at `limit:10` (or go straight to the spill-file projection where a bash mount exists). Project to `id, status, tradingsymbol, exchange, trigger_values, quantity` immediately.
- `condition.last_price` is the price at creation; compute proximity from live LTP.
- Place-then-delete: place the replacement GTT first, verify with `get_gtts`, then delete the old one. While `delete_gtt_order`/`modify_gtt_order` reject `trigger_id` (open since 30-Sep), output the exact GTT ids for the user to delete in Kite web.
- Corporate actions: scan held symbols for upcoming ex-dates (bonus, split, demerger, dividend) and re-score GTT proximity against the post-adjustment price. Web search is unreliable for fresh record dates, so say "unconfirmed" rather than guessing.

**3c. Broker session handling** (session-open, daily-briefing):
- Test every broker independently before emitting anything. Report per broker (live / needs login / outage) and give a login link only for the broker that failed.
- Never output a login URL that a login tool did not return.
- One silent retry on the first kite call of a run when it returns `-32001`.
- "Please log in first" means auth, so request a login. "Failed to execute" after a login means an outage: don't re-prompt; mark GTT and trade-audit items "unverified, broker outage" and carry them forward with a count of consecutive unverified runs.
- If the plugin Kite server keeps returning the same session_id after a fresh authorise, call it a stale session, fall back to a standalone `kite` server if one is connected, and say so.
- Kotak: the QR binds to the `get_login` session id minted in this run; validate that id only.
- IBKR: `get_account_summary` first, `get_account_balances` optional; if both fail, estimate from positions plus last-known cash and label it.
- Kotak `get_limits` small negative available margin: treat as zero.

**3d. Data and context**
- Read every `.md` at the working-folder root (not a fixed list), plus the latest snapshot.
- Per-symbol quantity snapshot each run; diff against it to detect trades made between sessions (`get_orders`/`get_trades` only cover today). Use `meta.gtt: true` to tell GTT fills from manual trades.
- Verdict diff: compare today's orders against verdicts in `portfolio-profile.md` (14-Oct SBIFUNDS case).
- SIP status cannot be read from the connectors; say so rather than infer a contribution amount.
- Record Kotak MF folio count per run so a partial return is mechanically visible.
- Any derived percentage carries its denominator label (e.g. "% of Zerodha equity").
- Cross-check search-asserted dates against the environment date; same-day FX, index and Asian session levels from search get flagged as low-confidence.

**3e. Allocation and cash logic**
- Buffer vs war chest: the profile records where the cash buffer is held. If it is outside the broker, broker cash is deployable and is not gated by the buffer rule. Update house rule 5 and risk-check to read this from the profile.
- War-chest deployment: support a staged, level-triggered table in the profile (levels, % of corpus, destination basket). crash-protocol reads it instead of inventing tranches.
- Rate-sensitivity map: macro-brief maps rate/FX/crude moves to the user's held sectors. *Source content still to be collected from the 30-Sep session in progress.md.*

### W4. Plugin drafts, user executes; two editions (roadmap fix 4)

**Drafting outputs** (both editions):
- GTT plan table: `symbol | action (place/delete) | GTT id | type | trigger(s) | limit | qty | reason`.
- Basket row list: `symbol | exchange | qty | LIMIT price | basis`, ordered for entry in Kite web, with a total and the cash check. JSON export as an option. There is no basket MCP tool and the private `/oms/baskets` route is off-limits.

**Full edition** (`portfolio-copilot`, GitHub marketplace): today's plugin. Bundles Kite and Kotak MCPs and keeps the PreToolUse order gate. It may place GTTs after per-order confirmation.

**Lite edition** (`portfolio-copilot-lite`, directory candidate): same skills and agent, no `.mcp.json`, no order execution step. Skills detect whether order tools exist; if not, they stop at the draft. README tells users to add broker connectors themselves.

**Single source:** skills are written edition-neutral, and the build script assembles both editions, so nothing is duplicated by hand. `marketplace.json` lists both.

### W6. get-started scaffolds per-user state (roadmap fix 6)

get-started creates in the working folder:
- `portfolio-profile.md`: goals, risk, thresholds, where the cash buffer lives, allocation targets, GTT policy overrides, war-chest table, per-symbol verdicts.
- `progress.md` with a "Start here" block (goal, current state, next actions, decisions owed) at the top, dated log below.
- `learnings.md` (or a Learnings section in the profile): one line per hard-won lesson.

Skills read these at start and append to `progress.md`; they never silently edit verdicts. The `PortfolioReviews/` per-day files stay optional.
